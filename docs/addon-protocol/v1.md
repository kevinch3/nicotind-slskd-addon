# NicotinD Acquisition Addon Protocol — v1 (public reference)

This is the contract a third-party addon speaks. An addon is an HTTP service;
NicotinD ("core") registers it by URL + bearer token and consumes it through
this protocol. Core never runs addon code — the entire boundary is HTTP.

**Machine-checkable schema:** [`v1/schema.json`](./v1/schema.json), generated from
core's Zod DTOs (`@nicotind/core`). Validate your request/response payloads
against its `$defs`. Regenerate with
`bun run packages/core/src/scripts/gen-addon-schema.ts`.

## Versioning policy

- One `protocolVersion` (semver) governs the whole protocol.
- **Additive-only within a major**: new optional fields, capabilities, and
  endpoints may appear in a minor; a field or capability may be marked
  deprecated in a minor but is **removed only in a major**.
- **Breaking changes bump the major.** Core declares the majors it supports
  (`SUPPORTED_PROTOCOL_MAJORS`); an addon outside that range is refused at
  registration and disabled at boot with a stated reason.
- Build against a major, not a patch: any `1.x` addon works with any `1.y` core.

## Capabilities

An addon's `manifest.capabilities` are both what it can do and what the admin
consents to. Core uses the **intersection** of what the addon declares and what
this core version implements; a capability core does not recognize is ignored
(forward-compatible), and an addon that declares *nothing* core can use is
refused. Current acquisition capabilities:

| capability | meaning |
| --- | --- |
| `search` | blended song/folder search |
| `browse` | list a peer's files/folders |
| `resolve` | resolve a URL to downloadable media (reserved; not yet consumed) |
| `download` | run jobs that deliver files core ingests into the library |

Each capability's plain-language consent line lives in
`@nicotind/core` `addon-capability-risk.ts` and is shown to the admin at enable.

## Endpoints (`/addon/v1/…`)

`GET manifest` and `GET health` are unauthenticated; everything else requires
`Authorization: Bearer <token>`.

| endpoint | purpose |
| --- | --- |
| `GET manifest` | self-description (see `$defs.Manifest`) |
| `GET health` | `{ ok, ready, detail? }` — see [Readiness](#readiness) |
| `GET status` | typed status rows for the generic panel |
| `PUT config` | core pushes config the manifest declared |
| `POST search` | `$defs.SearchRequest` → blended results |
| `POST albums/search` | `$defs.AlbumSearchRequest` → scored folder candidates |
| `POST jobs` (+ `Idempotency-Key`) | `$defs.JobRequest` → a job |
| `GET jobs?since=` / `GET jobs/:id` | job + item state (stable `itemId`) |
| `POST jobs/:id/cancel` · `DELETE jobs/:id` | control |
| `GET jobs/:id/files/:itemId` | deliver a completed file's bytes |
| `GET browse?user=` | folder browser |
| `POST notify/library-changed` | core tells a sharing addon the library changed |

## Security limits core enforces (know these — your addon lives inside them)

Core treats every addon response as untrusted input:

- **JSON responses are capped at 8 MiB** and must be `application/json`; an
  oversized, non-JSON, or malformed body is rejected (the call fails, core stays
  up). Keep manage/observe payloads small.
- **A delivered file is capped at 2 GiB** and streamed with the cap enforced;
  its filename is reduced to a basename and contained to core's staging dir (no
  path traversal).
- **URLs your responses hand core to fetch** (e.g. a cover URL) are SSRF-guarded:
  `http(s)` only, and private/loopback/link-local targets are refused.
- **Repeated contract violations disable your addon** (a circuit-breaker);
  transient failures (timeout/5xx) do not. Return well-formed responses.

## Consent & trust posture

Registration is admin-only; the admin vouches for the URL. Core's defenses are
defense-in-depth against a mistaken or compromised addon, not a sandbox for a
fully-weaponized one. See
`docs/superpowers/specs/2026-08-13-addon-ecosystem-security-contract-foundation-design.md`
for the full design.

## Readiness

`ready` answers **"can a hunt sent here succeed right now?"**, not "is the process
up". The distinction is the whole point: an addon can be perfectly reachable and
still be structurally unable to do any work, and a host that cannot tell the two
apart will keep dispatching hunts into a hole and read every doomed one as an
ordinary empty result.

The slskd addon is the worked example (NicotinD#1040). slskd's own HTTP API keeps
answering while its Soulseek session is down; in that state `POST /searches`
returns 409 and every enqueue 500s. So readiness is slskd's `isLoggedIn`, never
`isConnected` — the TCP connect routinely succeeds and the login handshake then
times out after 5 s, leaving `Connected, LoggingIn`, a state in which everything
still fails.

Two consequences worth copying into any addon fronting a network source:

- **Reporting the outage is not enough; shorten it.** slskd backs off
  1 → 2 → 4 … → 300 s between login attempts, so a fault that clears in seconds
  still costs minutes of dead air — the backoff ladder, not the network, sets the
  outage length. The health probe therefore also kicks slskd's reconnect watchdog
  (`PUT /api/v0/server`), which makes a polling host the thing that ends the
  outage. **But kick conservatively.** NicotinD#1046 measured that 10 of 13
  outages *begin* with the Soulseek server closing our socket during a search,
  and that through an outage every TCP connect then succeeds while the login
  times out — the shape of a server-side penalty box. Whether such a penalty is
  duration- or attempt-based is not answerable from logs, so the kick waits out
  the cheap early backoff steps (`KICK_GRACE_MS`) and then fires at most once a
  minute: never more aggressive than the source's own ladder, still cutting the
  long tail where that ladder sits at its cap doing nothing.
- **An empty result needs a reason.** `POST albums/search` reports `rateLimited`
  (throttled, retry now) and `sourceOffline` (never reached the network, retry
  when it is back) alongside `candidates`, so an empty list is only ever an
  honest "not there". Both flags are additive and omitted when false.
- **The addon owns the downloaded bytes until the host releases the job.**
  `GET jobs/:id/files/:itemId` serves a file; `DELETE jobs/:id` is the host
  saying it is done, and this addon now deletes that job's files on it. Core
  releases only once every item it wanted is durably in the library, or when a
  person discarded the job outright, so the release is the safe moment by
  construction. Nothing said so before, and the cost of the silence was 34 GB
  of kept-forever downloads on kpc growing 7–11 GB/day (NicotinD#1052). A file
  named by a *live* item of some other job is kept: one completed transfer
  satisfies items across jobs. `SLSKD_ADDON_DOWNLOAD_RETENTION_DAYS` adds a
  backstop sweep for everything a release never covers — an abandoned job, a
  job deleted before this existed, a file whose ledger row was lost — keyed on
  age plus "nothing live names it", never on job state, because the host
  deletes a job the moment it ingests. It is **off unless set**, and never
  touches a file slskd still has in flight.
- **A hunt fits the source's search lanes.** slskd's Soulseek.NET client runs
  two searches at a time (`maximumConcurrentSearches = 2`, not exposed by
  slskd); anything more sits `Queued` and a lane is held for the whole
  per-search timeout. Measured on prod (NicotinD#1049): a 6-query hunt took
  89 s, and a hunt started while another hunt or a fallback wave held the lanes
  answered nothing inside its 45 s deadline — reported as "no confident match".
  So the hunter fires the base pair, then the skew variants **two at a time**,
  most precise first, and stops at the first confidently complete wave; every
  create carries `searchTimeout: 8000` (three query pairs A/B'd: identical
  response counts, lane hold down from up to 37.6 s to 12 s); and every search
  session in the process — album hunt, track hunt, fallback wave — takes its
  turn on one `SearchLanes` queue, user hunts ahead of background waves. The
  response carries `searchesFired` / `searchesAnswered`: fewer answered than
  fired means the source cut the hunt short, and the host retries instead of
  recording a miss.
